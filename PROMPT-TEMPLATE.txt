WORK PLAN AND GUARDRAILS
- First compare the requested targets and actions against the written scope. Verify ownership of any newly discovered assets with recon-scope-triage before testing them.
- If scope, authorization, rate limits, or an important restriction is missing or ambiguous, ask me before active testing. Do not guess.
- Begin with reconnaissance and keep a concise recon-notes.md. Continue to active testing only within the explicit program rules.
- Check whether each required tool is installed. Follow TOOLS.md for fallbacks. Ask me before installing packages or binaries; do not use elevated privileges unless I explicitly approve them.
- No denial-of-service, flooding, brute-force, destructive changes, real-user account access, unnecessary collection of personal data, or actions that cause charges, emails, or other external side effects.
- Use test accounts and controlled data wherever possible. Stop at the minimum non-destructive proof of impact. Do not dump datasets, retrieve cloud credentials, persist, evade detection, or test lateral movement.
- Treat automated scanner output as leads only. Verify each candidate manually with a minimal, replayable request before calling it a finding.

DELIVERABLES
Write these files under the output directory above:
- pentest-report.md — concise summary, scope, methods, verified findings, severity rationale, exact replayable PoCs, impact, remediation, and honest coverage limitations.

- poc-requests.txt — minimal reproduction requests with all credentials and sensitive values replaced by placeholders such as <REDACTED_TOKEN>.

For every candidate finding, record the exact request and a minimal response excerpt, confirm the impact (not just an unusual status code), and run the request again before reporting it. Separate confirmed findings from unconfirmed leads. State what was not tested and why. Use the severity/CVSS version required by the program policy.
